# Claim session loot into a player inventory

For v1, a loot container owns only items created for that server session. The only permitted cross-inventory transfer is **loot container to player inventory**. A player inventory is owned by that player's Scribe profile; a loot container is owned by the server process and expires with it. Moving a durable player item into a session container would allow shutdown to erase its only durable owner, so that direction requires a later durable escrow or persistent container design. Container creation must not copy an item already owned by a player or another container.

The server accepts a claim only after player data is ready. It then reserves the container, reads both *current* snapshots, checks both expected revisions, and computes both successors with the shared grid transfer. This commit section must not yield. The player successor is written once inside a Scribe transaction; only after that transaction confirms success does the server replace the container snapshot. Both revisions advance once. The reservation covers Scribe's callback dispatch and the final container replacement: an observer can reenter during transaction completion before the caller gets control back. Every container claim, creation, expiration, and mutation must respect the same reservation. A busy container returns a retryable failure; a stale revision returns a stale failure. Invalid state, missing items, no fit, or revision overflow leave both accepted snapshots unchanged.

If Scribe reports a rolled-back transaction, the container stays unchanged and the claim fails. An unexpected throw after the player write has an uncertain commit point: the server must inspect the current player snapshot before releasing the reservation. If it can prove the item remained absent, it may release the container; if it can prove the item is in the player snapshot, it finalizes container removal. Otherwise it quarantines the container item from further claims and reports an indeterminate result for operator diagnosis. It must never compensate by blindly removing the player item or making the container item available again. A successful claim returns the new revisions; the player's Scribe replication and the container's eventual replication remain separate presentation paths.

Scribe 2.3.0 transactions are atomic in one player's memory, not across owners and not on the DataStore. A success response means one owner in the live server; it does not promise that the player's latest snapshot was saved before a crash. Scribe's ordinary save and shutdown behavior applies to the player, while all unclaimed container items disappear when the server ends. A per-claim forced flush would yield between owner changes and introduces an uncertain result when a save times out but later succeeds, so v1 does not add one. Live DataStore restoration and shutdown durability remain separate verification work for the durable-player outcome.

The server seam is `Inventory.TakeFromContainer(player, containerId, itemId, expectedPlayerRevision, expectedContainerRevision, timeout?)`. It returns either the committed player and container revisions or a stable rejection reason. The Inventory feature owns the session container store; creation and seeding are server-only. A client request protocol and container replication are later work.
