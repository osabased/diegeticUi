# Bind world loot to a server-checked instance

A world container has one server-created session inventory and a generated lookup ID replicated on its world part. The ID identifies the inventory but grants no access: inspection and claims require the server-observed player to be present, alive, and near the still-present part. The claim path checks again after player-data readiness, before its reserved commit. Removing the part closes new access immediately; an in-flight claim finishes its reserved commit or rejection before its session inventory is discarded. This keeps ownership unambiguous when removal occurs during transaction callbacks.

The Blink inspect function returns a validated snapshot and revision only to the requesting eligible player. The claim function returns both committed revisions or a stable rejection reason. Both paths recheck eligibility on every request; neither accepts a client-supplied snapshot or treats a future ProximityPrompt activation as authorization. Player inventory continues to reach the client through Scribe. The distance rule stays in the server access function so presentation can change without moving authority to the client.

Inspection is request-scoped. There is no server push when a player walks away or a part expires. An open view must close or refresh when its next inspect or claim returns `NotEligible` or `ContainerMissing`; the presentation layer must also dismiss promptly when its observed world part disappears or leaves local range. A claim success carries revisions rather than a second player snapshot: Scribe remains the player-state delivery path, and the container view needs a fresh inspection before showing its next state.
