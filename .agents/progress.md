## Observations

- `tests/studio/InventoryPlayerData.spec.luau` constructs the Scribe schema in a mock bundle; it does not exercise a server player load.
- Studio server probes against installed `ericplane/scribe@2.3.0` seeded disposable `ProfileStore.New(name, {}).Mock` sessions, ended each seed session, then used `PlayerDataSchema.createBundle({ Mode = "Mock", ProfileStoreIndex = name, ProfileKeyPrefix = "Probe_" })` and the real player. Before load, `GetState` was `Loading` and `Get(player)` errored. An empty profile yielded `{ Revision = 0, Items = {} }`; a saved profile with revision 7 and one item loaded with the same fields through `WaitForData(player, 10)`.
- In the same mock server probe, `data.Inventory.Set` replaced the entire revision/items value. `Set({ Revision = "oops", Items = {} })` threw `expected number, got string` and left the accepted snapshot unchanged. A forced error after `Inventory.Set` inside `Server.Transaction` returned `false, error` and restored the prior snapshot. `Server.Flush(player, { Force = true, Timeout = 10 })` returned true in mock mode; transaction success alone is not a durability claim.
- A preseeded stored `Inventory.Revision = "bad"` produced a ready accessor with that string under the current bundle options, with `PROFILE_SCHEMA_VIOLATION` logged. A preseeded pair of overlapping items also loaded unchanged; `Grid.place` rejected that snapshot with `InvalidSnapshot` using a matching definition and 4 by 4 grid. Scribe's current schema does not enforce spatial validity, and `PlayerDataSchema.createBundle` does not pass `SchemaPolicy = "Reject"`.
- A disposable `Mode = "NoSave"` bundle with an empty key and Studio API access disabled returned `nil, "load-failed"` from `WaitForData`; subsequent `Get(player)` errored with no data session. The load gate must treat nil as unavailable and must validate a nonnil snapshot before admitting mutation work. Each probe ran in a fresh play session because `Server.Stop()` closes the shared ProfileStore module to later loads in that session.
- A connected M006 probe against pinned Scribe 2.3.0 showed that a disposable bundle with a separate profile store but the default transport channel can receive an unrelated `Init`. Giving the mock bundle the same distinct `TransportChannel` on both runtimes isolated its revisions from the production bundle.
- A guarded Studio diagnostic investigation reproduced `Script that implemented this callback has been destroyed while calling callback` in 2 of 5 full-suite runs after all 23 assertions passed; retained failing logs include `.verify/studio-diagnostics/1790133489-000.log` and `.verify/studio-diagnostics/1790133545-000.log`. The diagnostic guard correctly failed those runs, while direct Lest runs can exit successfully despite the warning.
- A reduced Fusion-construction and client-snapshot Studio selection also reproduced the warning intermittently, while each spec alone and 12 no-op Studio runs were clean. Further subset trials yielded inconsistent clean samples, so neither project callback ownership nor Lest/Studio teardown was established. The temporary diagnostic harness was removed without changing production code or the guard; repeat subset trials require new owner-level evidence to be useful.
- Pinned Scribe 2.3.0 documents and implements `Server.Transaction` as a one-player, non-yielding in-memory transaction. Its success does not confirm a DataStore save; `Flush` yields and a timeout can precede a later save. `RunTransaction` dispatches callbacks before returning success, so a container commit needs a reservation that remains held through callback dispatch and source replacement.
- Two fresh Studio server sessions used disposable, isolated Scribe mock bundles with a real player. A proposed container-to-player commit harness accepted a first item (both revisions 0→1), rejected stale expected revisions without a write, rolled back a forced error after `Inventory.Set` while retaining the source item, and serialized two competing claims into one acceptance and one stale rejection (both revisions 1→2). A second harness observed an inventory callback reenter before container replacement; a reservation returned `busy` and prevented a second claim. These are design probes, not production transfer implementation or live DataStore evidence.
- A guarded Studio test using pinned Scribe 2.3.0's isolated mock store accepted a production inventory rotation, confirmed a mock flush, ended and reopened the player session, and recovered the exact revision, items, placement, and rotation through production readiness validation. It does not establish live DataStore durability or autosave, leave, and shutdown behavior.

## Open Questions

- How should a malformed or spatially invalid stored inventory be surfaced to a player or operator while keeping mutations closed? Live DataStore restoration and save durability remain unverified by the disposable mock probes; M006 verified client replication only through an isolated mock bundle.
- A removed or footprint-changed catalog definition can make a stored inventory fail validation and close server mutations. A catalog migration or recovery policy is needed before shipping incompatible definition changes.
- Which script owns the intermittent late Studio callback? The diagnostic selection trials narrowed where it appears but did not identify the callback; a callback-owner trace or deterministic reproduction is needed before making a source fix.
